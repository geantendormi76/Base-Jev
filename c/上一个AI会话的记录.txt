# 封印一：偷懒的代价——“2 秒代数投影”带来的因果反噬（数据血统问题）

报告中一针见血地指出：**“你的 5×5 网格实际上只有 6 个格子真正被使用，L4/L5 根本没出来。”**

为什么会这样？**根因就在我们刚才为了省时间，选择的【方案 1：2 秒钟代数重投影】！**

* **我们刚才做了什么？**
  为了不等 27B 跑 5 个小时，我们写了一个 Python 脚本，用 `if method == "GET": impact = 1.8` 这种硬编码规则，把原来的单维度分数“强行拆成”了双维度。
* **0.6B 模型学到了什么？**
  0.6B 模型非常聪明，它在 5 轮微调中，**完美地逆向工程（Reverse-engineered）了我们那个 Python 脚本里的 `if-else` 规则！**
  因为我们的脚本在处理那 150 条真实爱快端点时，给出的 Impact 分数基本都卡在 1.8 ~ 3.5 之间，根本没有给真实端点打过 5.0 分。
* **真相大白**：

# 封印二：物理架构的“单头复用”瓶颈（架构解耦问题）

报告第十三节指出了一个极其致命的架构隐患：
> *“两个维度实际上还是调用同一个 `forward_score()`。这更像是用 Query Prompt 把一个 scorer 当成两个任务来调用，而不是真正的双正交训练。”*

* **当前的物理拓扑**：
  我们虽然在输入端问了两个不同的问题（破坏力？敏感度？），但在 0.6B 模型的最后一层，它们流经的是**同一个 `ScoreOrdinalHead`（同一个 $1024 \times 5$ 的线性分类矩阵）**！
* **为什么这会卡住 95% 的精度？**
  “破坏力”评估的是底层操作（写磁盘、删库、重启）；
  “敏感度”评估的是数据资产（密码、Token、日志）。
  这是两个**完全正交的语义空间**。强迫同一个线性矩阵同时学会这两种截然不同的映射，会导致权重矩阵内部发生严重的**表征纠缠（Representation Entanglement）**。
* **破局之道**：
  在真正的工业级双正交架构中，必须在 `UnifiedDecisionHeads` 中物理拆分出两个独立的头：
  - `impact_head = ScoreOrdinalHead(1024, 5)`
  - `sensitivity_head = ScoreOrdinalHead(1024, 5)`
  让两组独立的权重各自负责一个维度，互不干扰，精度才能瞬间飙升！

# 封印三：伪 AST 切片的“邻居污染”（特征纯度问题）

报告第十五节再次鞭挞了我们的切片提取逻辑：
> *“你现在依旧使用找到 path 后，再向前/向后截取一段字符串... 这仍然不是 AST 精确上下文。”*

* **当前的特征提取**：
  我们把窗口缩小到了 220 字符，但这依然是**物理字符串截取**。
  如果源码是这样的：
  ```javascript
  api.get("/admin/role/get"); api.post("/admin/role/delete", {id: 1});
  ```
  即使是 220 字符，`delete` 这个极度危险的词依然会漏进 `/admin/role/get` 的上下文中！
* **为什么这会卡住 95% 的精度？**
  模型看到了 `delete`，它的注意力机制就会被这个高危词汇吸引，从而把原本安全的 `GET` 接口的破坏力强行拉高。这就是报告中提到的 **Neighbor-Context Leakage（邻居上下文泄漏）**。
* **破局之道**：
  必须在 `distiller` 中彻底启用 `tree-sitter`，**只提取当前 `CallExpression` 节点内部的文本**，把前后的分号、其他函数调用全部在 AST 语法树层面物理切断！
